## 1. 这个项目是什么

**一句话**：硬币判官是一个「消费反思」向的个人记账 PWA——不只是记流水，而是每笔消费都要回答"值不值"，买后 N 天还会被追问"这东西你用到了吗"，月底用账户余额反推真实花销，帮用户管住冲动消费。

**口号**：记一笔，判一笔。

**用户画像**：作者是大学生（月预算 1500），但产品不局限于学生群体。中文界面，手机优先，桌面端以手机宽度居中展示。

**商业模式/运营**：纯个人项目，无后端、无账号体系、无服务器成本，数据 100% 存在用户浏览器本地。

## 4. 架构与核心设计

### 4.1 总体形态

纯前端 SPA：React 18 + TypeScript + Vite 8 + Tailwind v3 + zustand v5 + React Router v6（**HashRouter**，因为没有任何服务端路由）。

**没有后端**。所有数据经 zustand `persist` 中间件序列化为单个 JSON，存进 `localStorage` 的 key `coinjudge_v2`。铁律：**业务代码任何位置禁止直接调用 localStorage**，必须走 `src/store/store.ts` 的 action（`lib/notify.ts` 之类的基础设施也不例外，目前全仓库零违规）。

### 4.2 数据模型（`src/store/types.ts`）

8 个"表"全部平铺在一个 state 对象里：

| 字段 | 类型 | 说明 |
|------|------|------|
| `meta.version` | 2 | 数据格式版本，导入校验用 |
| `settings` | Settings | income（月收入）、budget（月预算）、openingBalance（期初余额）、registerDate（注册日，见下）、reminderDays（回顾天数 1–30）、theme（auto/light/dark）、notifyEnabled |
| `accounts` | Account[] | id/name/icon（图标 key，如 `wechat`）/balance |
| `records` | Record[] | **核心表**：id/amount/name/categoryId/mood（impulse😡/need✅/reward🎁）/tag（worth/unworth，只有两桶）/date/reminderDays（创建时快照！）/reminded/used（null/true/false）/createdAt |
| `subscriptions` | Subscription[] | 会员订阅：name/icon/amount/renewDate/cycle（month/year）/autoRenew |
| `categories` | Category[] | id/name/emoji/color/builtin；首次启动播种 6 个内置分类，内置可改名改色不可删 |
| `principles` | string[] | 消费原则，按数组下标操作 |
| `monthlyHistory` | MonthlyRecord[] | 每月对账结果快照（含 actualSavings 等 6.5 公式产物） |

**关键隐藏规则**：
- `registerDate` 在"首次同时填完收入+预算"时由 store 自动写入（`withRegisterDate`），**注册当月的收入/预算按剩余天数折算**（proRata），次月起全额。改这块逻辑前先读 `derived.ts` 的 `getMonthInfo` 和 verify-formulas 里的 B 组用例。
- `records[].reminderDays` 是创建时从 settings 快照的，事后改回顾天数不影响存量记录——这是有意设计。
- zustand persist `partialize` 只持久化数据字段，函数不进 localStorage；persist `version: 2` 与 `meta.version: 2` 是两处独立编号，目前保持一致。

### 4.3 公式层（`src/store/derived.ts`，全部是纯函数）

所有算钱逻辑集中在 derived.ts，**页面不许自己算**。核心公式（需求文档 6.1–6.5）：

- `effectiveBudget/effectiveIncome`：注册当月 × proRata（剩余天数/当月天数）
- `monthShopping / monthSubs`：本月购物支出 / 会员月摊（年费 ÷12）
- `estimatedAssets`：期初 − 本月购物 − 本月会员（对账前的"估算"口径）
- `expectedSavings`：收入 − 预算（对账前存钱卡显示"预计能存"）
- `calcReconciliation`（6.5 对账核心）：录入各账户期末余额后
  - 实际总支出 = 期初 + 收入 − 期末合计
  - 推算日常支出（看不见的花销）= 实际总支出 − 购物 − 会员
  - 实际存了 = 期末 − 期初（对账后存钱卡切换为这个"实际"口径）
- `pendingReview`：`!reminded && 今天 − date ≥ 该条的 reminderDays` 的购物记录（原则页待回顾 + 系统通知都用它）
- `tagStats / moodDistribution / categoryDistribution`：统计页数据源

verify-formulas.mjs 里的 A/B/C/D 四组用例就是这四类场景的手算对照，改公式必须同步改脚本。

### 4.4 关键数据流

**记一笔**：TabBar 中央 + 号 → `window.dispatchEvent('open-record-modal')` → 全局唯一 `RecordModal`（挂在 App.tsx，z-100）→ Numpad 金额 → 分类（读 store.categories）→ 情绪 → 审判（值/不值）→ 日期（DateRoller 滚轮）→ `addRecord` → 金库大数字 `.success-bounce` 弹跳。

**回顾闭环**：到期的记录出现在原则页"待回顾"→ 点"用到了吗"弹窗 → `reviewRecord(id, used)` 同时置 `reminded=true` → 统计页"值不值"只统计 used≠null 的。

**对账闭环**：Monthly 页逐账户录期末 → 实时算 6.5 → 复盘文字 → `upsertMonthlyRecord` + 期末合计滚动成为新的 `settings.openingBalance`。

**备份**：`lib/backup.ts` 导出 `{app:'CoinJudge', version:2, ...}` JSON；导入用 `parseBackup` 严格校验（**只认 v2，明确拒绝 v1 备份且不做迁移**——这是需求文档的决定，别心软加迁移）→ `importAll` 整体替换（保留 meta）。清空流水可选全部/日期范围，UI 强制手动输入"确定"。

**返回键联动**：`lib/useBackClose.ts` 模块级栈 + `history.pushState`，嵌套弹窗按返回键只关最上层。新弹窗都要接这个 hook（现有：RecordModal/DateRoller/原则回顾/资产添加/清空确认/分类编辑删除/Monthly 分享）。

**通知**：`lib/notify.ts`，App 启动 + 每 30 分钟查一次 pendingReview，`Notification` API 发系统通知，同日最多一条。网页通知可靠性一般，需求文档已定：微信提醒是远期不做。

## 6. 设计系统（做 UI 前必读 `docs/设计规范.md`）

铁律摘要：

1. **颜色只许用 CSS 变量**（`var(--color-*)`）或 Tailwind 映射类（`bg-primary`、`text-text-2`）。全代码扫描零硬编码 hex（例外仅：index.css 变量定义、图标/插画/分享卡这类"图片"）。改完可用 `grep -rn "#[0-9a-fA-F]\{3,8\}" src/ --include="*.tsx"` 自查。
2. **布局永远 430px**：`.shell` max-width 430 居中，桌面端也不放大（v2.0 的双栏布局被否了，别加回来）。固定定位元素用 `.shell-fixed` / `.modal-fixed`。
3. `html` 有 `scrollbar-gutter: stable`——**别删**，删了切页面会左右跳。
4. 银行卡是核心视觉：真实卡比例 + 百分比圆角，桌面端绝不拉宽。
5. 小怪兽是品牌 IP：纯白身、黑方眼、像素风 `crispEdges`，不许改成圆角渐变"现代风"。
6. 图标全部内联手写 SVG；**唯一例外是账户品牌 Logo**（微信/支付宝/花呗/币安/OKX 用官方下载版，裸放无底框）。
7. 动效只做反馈不做装饰，参数都在设计规范第 9 节，别新增花哨动效。
8. 深色主题 = `<html>.dark` class + 变量切换，`settings.theme` 三态，App.tsx 的 useTheme 负责（含 auto 监听系统）。

## 7. 开发规矩（前车之鉴，都是踩过的坑）

1. **commit 规范**：`[P1]/[P2]/[P3]/[fix]/[feat]/[docs]/[chore]` 前缀 + 一句话说清改了什么。git 提交需要 `-c user.name -c user.email`（仓库没设本地身份）。
2. **改数据层必跑 3 个 verify 脚本 + `npm run build`**，全绿才提交。verify 脚本的原理是把 src 的 `.ts` 复制到 `scripts/.tmp/` 补全扩展名后用 Node 原生跑（所以 Node 不能降级；`.tmp/` 已 gitignore）。
3. **构建偶发慢**：`tsc -b` 首次可能超过 2 分钟，超时就重跑，不是卡死。
4. **Git Bash 用 `npm.cmd`**；起预览服务器验证后**必须在同一条命令里 kill 掉**（曾残留两个 node 进程占端口，被用户严令禁止留后台）。Windows 上 `kill %1` 杀不掉 vite 子进程时，用 `netstat -ano | grep <port>` 找 PID 再 `taskkill //PID <pid> //F`。
5. 需求文档有两份在仓库外（`D:\Coin Judge\硬币判官v2-重写项目文档.md` 和 `硬币判官v2.1-需求文档.md`），**v2.1 是唯一现行需求来源**，第 13 节有全部问卷决策依据。旧版代码在 `D:\Coin Judge\旧版参考\` 仅供参考，别往里写东西。
6. 用户是编程新手：汇报用大白话，禁用术语轰炸；每完成一块给可自查的验收点。
7. 不要引入重型依赖。目前依赖极精简（router/zustand/html2canvas + 构建链），连图表库都没有——折线图是手写 SVG，保持这个风格。

## 9. 下一步建议（如果要继续开发）

优先级纯属建议，动工前先跟作者确认：

1. **真实使用反馈收集**——作者刚开始用，大概率冒出体验问题，优先修这些
